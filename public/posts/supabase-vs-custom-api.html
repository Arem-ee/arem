Why I chose Supabase over a custom API for a solo build

TL;DR

The problem: two weeks of backend, zero features

For the first two weeks of building Propeida, I was convinced I needed a custom backend. I set up a Node server with Express, connected it to Postgres, wrote authentication middleware, built CRUD endpoints for every table, and configured row-level security by hand. It was going well until I realized I had not shipped a single user facing feature in fourteen days. All I had was a working API that nobody could use.

That was the moment I decided to rewrite everything on Supabase in one weekend. The decision felt like giving up at the time. I had already invested two weeks into the custom backend, and starting over felt wasteful. But looking back, it was the single most important technical decision I made on the project.

What I gave up

A custom API gives you full control over every layer. I could structure the database exactly how I wanted, optimize every query, write custom validation logic, and design the API around the specific needs of the product. With Supabase, I had to accept their conventions. Authentication works their way. Row level security uses their policy syntax. The database schema has to fit their tooling. For someone who likes control, this felt like a real sacrifice.

I also gave up the ability to customize performance. With a custom backend, I could add caching layers, write complex joins, and fine tune every database call. Supabase handles most of this for you, but it does not give you the same level of control over the details. For a project that needs to squeeze every millisecond out of the database, a custom backend is still the better choice.

What I gained

Speed: that is the honest answer. With Supabase, I had authentication working in an afternoon, so the user could sign up, log in, and start using the product the same day. With my custom backend, I had spent two weeks and still not shipped anything users could touch.

I also gained real time features without wiring websockets myself. Supabase handles subscriptions out of the box, which meant I could add live updates to the leaderboard without building a separate real time server. That feature would have taken me another week on a custom stack.

The row level security model was another win. Instead of writing middleware to check permissions on every request, I defined policies directly in the database. The rules were declarative and easy to read. A user can only update their own attempts. An admin can publish questions. These policies lived in one place instead of being scattered across API routes.

The SDK was the final piece. Instead of writing fetch calls and parsing responses, I queried the database directly from the frontend. Supabase generated TypeScript types from my schema, so I got autocomplete and type safety without writing a single interface by hand. It felt like the database and the frontend were speaking the same language, because they were.

The trade off

Supabase is not the right choice for every project. If you are building something that needs complex business logic on the server, heavy data processing, or fine grained control over performance, a custom backend is still the better option. If you are part of a large team with dedicated backend engineers, the conventions of Supabase might feel limiting rather than helpful.

But for a solo builder, the math is simple: every hour spent on backend infrastructure is an hour not spent on the thing users actually see. Supabase is not the most powerful option; it is the most efficient option when you are building alone and speed matters more than control.

The lesson

The lesson is not that Supabase is good and custom backends are bad; the lesson is that your stack should match your constraints. A startup with twenty engineers should not build on Supabase; a solo developer with limited time absolutely should.

I chose Supabase because I wanted to ship a product, not maintain an infrastructure. Two weeks of user facing work beat two weeks of backend plumbing every time. The best stack is not the most powerful one; it is the one that lets you ship the fastest while still being able to sleep at night knowing the thing will not fall apart.

Frequently asked questions
Is Supabase free to use?

Supabase has a generous free tier that includes 500MB of database storage, 1GB of file storage, and 50,000 monthly active users. For most solo projects, this is more than enough.

Can I migrate away from Supabase later?

Yes. Supabase is built on Postgres, so you can export your data and move to a custom backend if your needs outgrow the platform. The migration path is straightforward.

What are the main limitations of Supabase?

You give up fine-grained control over performance optimization, custom middleware, and complex server-side logic. For highly specialized use cases, a custom backend is still better.

How long did the migration take?

I rewrote the entire backend on Supabase in one weekend. The hardest part was unlearning the custom backend patterns and accepting the Supabase conventions.
